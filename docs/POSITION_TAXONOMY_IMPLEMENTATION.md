# 四维岗位分类：实现与后台修正

## 分类契约

一级类别单选，固定为：后端、前端、客户端、算法/AI、测试、运维/SRE、数据、安全、游戏、嵌入式/系统、其他。无法判断时 `category=null`；非研发岗位不塞进“其他”。

其余三维独立且多选：`specializations` 表示具体工作方向；`domains` 表示业务领域；`skills` 表示技术栈。词表及别名位于 `src/interviewlens/position_taxonomy.py`，版本为1。相同的“推荐”概念在不同维度有不同含义：专业方向使用“推荐算法”，业务领域使用“推荐”。

分类保存在每帖的 `post_position_profiles`，允许一帖多岗位，每条单选类别。旧 `positions`、别名、公司—岗位链接和摘要仍保留；分类不依赖它们是否已经归一正确。另有 `post_companies` 保存帖子涉及公司，使岗位未知的帖子仍可按公司浏览。历史公司关联从旧链接增量复制，尚未纠正旧公司抽取错误。

岗位字段包括原始/规范名称、四维结果、`status`、`source`、`needs_review`、逐标签证据、版本和输入哈希。

| 状态 | 含义 |
| --- | --- |
| classified | 有具体类别，直接参与筛选 |
| uncertain | 信息不足，类别为空 |
| out_of_scope | 非研发岗位，类别为空 |

`source=declared` 表示原文明示，`inferred` 表示内容推断。推断结果直接使用；人工修正结果优先于后续自动提取。证据来源进一步区分原文明示、职责、面试考察、个人项目、推断。“问了Redis”只表示考察过Redis，不当作岗位要求。

## 提取与校验

LLM 工具 schema 暴露固定类别及三个维度的合法枚举，后端再次校验，禁止自创类别。工具不暴露人工审核字段。

每个标签必须对应输入中的逐字证据。不存在的证据被丢弃，没有证据的类别降级为未明确，技术栈还必须实际出现在证据中；不因“C++”自动补Linux、FFmpeg等。CSIG、PCG、OD、日常实习等不能独立证明岗位。代码不能验证所有语义判断的真实性，推断及边界样本可能需要后台修正。

分类读取作者标题和清理后的正文。清理补充了完整页脚组合标记、独立评论操作栏等边界，防止推荐内容进入提取。系统设计题中的“推荐”“点赞”“收藏”不会仅因关键词被截断。该清理是针对已观察样本的规则，不能保证覆盖所有网页结构；原先已经提取的历史题目没有自动重新抽取。

Extractor 提示与缓存版本升级；分类与题目在同一事务写入。非法结构化输出标记提取失败，不把非法类别写入数据库。人工确认结果受到保护，自动重抽不会覆盖；检测到原文变化时保留旧结果，并保留原文变化的内部元数据；不因此隐藏分类或阻止筛选。

## 界面与查询

首页默认“按方向浏览”；“最新面经”和“检索”也支持四维过滤。一级单选、其余维度多选。相同维度是OR，不同维度是AND，并要求同一条岗位记录满足全部条件，避免多岗位帖子拼接条件。

所有分类直接参与筛选，前台不提供审核开关、待审核标记或分类实现说明。展开面经可看到原始名称及各标签的证据与来源。旧摘要保留在“原始岗位摘要”入口，未擅自按新类别重建或重新计费生成摘要。

API 新增：

- `GET /position-taxonomy`：词表、版本和分类覆盖计数。
- `GET /posts/{id}/position-profiles`：该帖的分类及证据。
- `/posts` 与 `/posts/search` 新参数：`position_category`、重复的 `specializations` / `domains` / `skills`，旧参数 `include_unreviewed` 仅兼容已有链接，不再影响分类可见性。
- `/posts` 新增 `position_profiles` 返回字段。旧公司、岗位筛选参数继续支持；旧 `category` 参数保留旧语义，新的一级岗位使用 `position_category`。

带四维条件的语义检索继续缓存查询向量，但不缓存完整结果，保证审核修改能立即影响筛选。无四维条件保留原有结果缓存。检索页的筛选可通过URL分享；首页和最新面经的四维筛选目前为页面内状态。

## 数据升级与历史预览

先应用 `sql/008_position_profiles.sql`，再启动新API/Worker。这是增量迁移，增加表及索引，不重命名或覆盖旧岗位、题目、题解和向量。没有自动把旧 `positions.category` 改成新枚举。

离线工具默认仅查询并输出JSONL，不调用LLM：

```powershell
python -m interviewlens.taxonomy_preview --output position-preview.jsonl
```

初始化表并保存历史规则结果：

```powershell
python -m interviewlens.taxonomy_preview --init --store --output position-preview.jsonl
```

规则更新时可增加 `--refresh-preview`，只更新未审核的历史预览，不能覆盖正常提取或人工确认记录。默认重跑不会覆盖已有记录。

## 后台手动修正

进入“机房 → 岗位分类管理”，按标题或帖子编号查找，选择帖子后可修改四个维度、添加或移除岗位记录，然后保存。空类别表示未明确，不强行塞入“其他”。保存后分类立即生效，前端相关缓存重新校验；后续自动提取不会覆盖人工修改。

新增 `GET /admin/position-posts?q=...`、`GET/PUT /admin/posts/{id}/position-profiles`。写入使用事务、与自动提取相同的每帖锁以及修订指纹，旧编辑副本返回409，要求重新加载。修改标签时清除不再适用的旧证据；人工新增标签不伪造原文引用。没有改动原题、题解或向量。

这些管理接口限制本机客户端，并拒绝非本机Origin。当前服务仅监听127.0.0.1；该限制不是完整登录鉴权，通过反向代理公开部署前仍需统一管理权限控制。

`needs_review` 等旧字段保留为兼容元数据，不构成审批流程或用户使用门槛。以下离线导入工具保留为可选批量人工修正方式。

## 人工审核导入

复制预览文件，仅为已经检查原文、修正分类及证据的记录增加 `"approve": true`。未明确批准的记录会跳过。可以保持单个 `profile`，或替换为 `profiles` 数组，表示一帖的多个岗位。原始 `input_hash` 必须保留。

```powershell
python -m interviewlens.taxonomy_review --input reviewed-positions.jsonl
```

导入对原文重新计算哈希，并检查标签证据。原文已变化、证据不支持、重复审核记录或非法类别会中止，整批事务回滚。成功后记录 `human_reviewed=true`，普通自动提取不会覆盖该帖已确认的岗位记录。该工具需要数据库访问，没有新增未鉴权的网页审核写接口。

本次未自动执行任何人工批准导入。
