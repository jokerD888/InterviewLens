# 岗位目录问题调查与分类方案

调查日期：2026-10-05。本次包含公司目录接口修复、岗位筛选交互改善，以及岗位分类方案研究。分类模型和历史数据迁移属于后续方案，尚未上线。

## 1. 公司点击为什么没有反应

点击公司会更新 URL 和公司选择状态，但 `/companies/{id}/positions` 返回 500。查询结果里的 `latest_posted_at` 是 Python `datetime`；缓存写入使用 `model_dump()`，随后 `json.dumps()` 无法序列化日期。前端原先没有展示请求错误，因此看起来像按钮失效。

修复：目录接口缓存使用 `model_dump(mode="json")`，缓存读取仍由 Pydantic 还原日期类型；岗位列表增加错误提示和重试入口。新增测试同时覆盖有日期、空日期、首次查询和缓存命中。

岗位界面默认显示关联面经最多的 12 项，提供搜索和展开，切换公司会清空搜索及展开状态。没有关联面经的条目不出现在筛选器中。全局请求上限从 200 提升到 500，覆盖当前数据；这仍是有界列表，未来超过 500 项应采用分页或服务端搜索。

这是界面和接口修复，并未修复已有岗位名称的语义质量。

## 2. 当前岗位如何产生

相关代码：

- `src/interviewlens/llm/prompts.py`：Extractor 提示词要求从面经提取公司和岗位，保留原始表达。
- `src/interviewlens/llm/schema.py`：`positions` 是自由字符串数组，没有受控岗位枚举，也没有每个岗位对应的原文证据。
- `src/interviewlens/llm/extractor.py`：调用 LLM 的结构化输出并进行格式校验。JSON 合法不能证明名称是岗位。
- `src/interviewlens/normalizer/resolver.py`：先查别名，再通过 BGE-M3 搜索已有实体。满足 0.92 相似度、字面关联和互斥规则可自动匹配，否则交给 LLM；未匹配时可能以新名称建立岗位。
- `src/interviewlens/agent/nodes/normalizer.py`：逐个传入名称，写入公司—岗位关联；没有把完整面经上下文传给实体归一，也没有用 `needs_review` 阻止待确认结果进入正式目录。

当前解决的是“两个名字是不是同一个实体”，缺少前置问题“这个名字是不是岗位”和另一层问题“这个岗位属于哪类”。此前增加的互斥规则能减少错误合并，但不能识别全部部门名、产品名和招聘类型，也不能自动建立岗位层级。

提取结果另有实习/校招/社招 `level` 字段，但当前帖子持久化路径没有把它落实为可筛选的独立维度，因此岗位名称仍携带大量招聘信息。

## 3. 本地数据证据

只读统计：234 个岗位实体；126 个仅关联一篇面经；26 个没有关联面经，208 个有关联面经。低频不是错误的判据。

抽查关联帖子标题及岗位名称可见：

| 名称或现象 | 问题 | 正确处理方向 |
| --- | --- | --- |
| CSIG、PCG、TEG | 组织部门不能直接充当岗位 | 独立部门维度，岗位不足时待确认 |
| 中国交易与广告 | 更像业务线，标题不足以确定实际职责 | 查正文证据，不凭部门推断岗位 |
| 文心一言 | 产品名不是岗位名 | 产品/领域标签，岗位另行提取 |
| 暑期实习生、日常实习生 | 表达招聘安排，没有明确职责 | 实习及招聘批次维度；岗位可为空 |
| AI 后端、后端开发、暑期后端AI开发 | 相近职责混入领域和招聘修饰 | 同一岗位大类，保留原始名称及标签 |
| Agent 前端开发、大模型测试开发 | 同领域不代表同职责 | 分别归前端、测试；领域均可为 AI |
| 热力工程师、无机材料研发 | 低频但可能是有效岗位 | 保留，按产品范围分组或标记范围外 |

这些是问题样本，不是全库标注结果；不能据此宣称岗位准确率或误报率。别名归一的少量正负样本评测也不能替代岗位抽取和分类评测。

## 4. 工业界与开源方案

没有适合所有业务的唯一最佳模型。对本项目，更值得借鉴的是分类与数据治理方式。

| 方案与一手资料 | 可借鉴的能力 | 在本项目的适用边界 |
| --- | --- | --- |
| [LinkedIn Talent Insights](https://www.linkedin.com/help/talent-insights/answer/a192040) | 把用户填写的职称映射为标准职称，再归入职能；技能及用工类型单独处理 | 借鉴维度拆分，不照搬其职业体系 |
| [ESCO 职业分类](https://esco.ec.europa.eu/en/classification/occupation-main) | 职业概念有层级、首选名称、其他名称、定义和技能关联 | 可借鉴稳定概念及别名结构；中文互联网岗位需要本地词表 |
| [O*NET-SOC](https://www.onetcenter.org/taxonomy.html) | 分层职业体系，配合职业名称及映射资源 | 适合提供通用层级参考，不直接等同于中国面经岗位 |
| [GLiNER](https://github.com/urchade/GLiNER) | 根据指定实体类型识别文本中的实体片段 | 可评测岗位/部门/技能抽取；不是完整的职业分类系统，中文效果需要实测 |
| [Sentence Transformers Retrieve & Re-Rank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) | 先召回候选，再用更精细模型重排 | 候选很多时可减少裁决成本；相似度不能单独证明岗位身份或同义关系 |

以上支持的项目建议是：受控岗位体系 + 原文证据抽取 + 多维标签 + 不确定结果审核。保留现有 LLM 和 BGE-M3 作为实现手段即可；当前规模没有证据支持必须新增一个重排模型或训练自有分类器。

## 5. 建议的数据模型和限定

把原始名称、岗位类别、技能、领域、部门、招聘类型分开保存。岗位大类供浏览筛选，原始岗位名供溯源和精确搜索。

| 原文表达 | 岗位类别 | 独立属性 | 不应做的推断 |
| --- | --- | --- | --- |
| Java 后端暑期实习 | 后端开发 | Java；实习；暑期批次 | 不创建“Java后端暑期实习”大类 |
| Agent 前端开发 | 前端开发 | Agent 领域 | 不因 Agent 改判后端或算法 |
| 大模型测试开发 | 测试开发 | 大模型领域 | 不与大模型算法合并 |
| 腾讯 CSIG 日常实习 | 待确认 | 腾讯；CSIG；实习；日常批次 | 部门不能证明具体岗位 |

首版围绕真实样本定义有限的大类，如后端、前端、全栈、移动端、嵌入式、测试、数据工程、算法、AI 应用、AI 基础设施、运维、安全、产品等，另设业务岗位和待确认入口。类别必须附定义、包含/排除示例及边界规则；“AI 应用”和“后端”等交叉情况要通过职责判定主类别，领域作为附加标签。具体类别数量应由样本覆盖和浏览需求决定，不以固定数量限制有效岗位。

建议限定：

1. **抽取限定**：岗位必须有标题或正文中的证据片段，保存来源与偏移。没有明确职责时允许为空；推断结果与原文明示结果分开。部门、产品、考试阶段、学校合作等分别提取，不能填进岗位字段。
2. **分类限定**：LLM 只能选择版本化的合法类别 ID 或待确认；后端检查 ID 及原文证据。模型不得自行扩充正式类别。新岗位名称可以保留，但进入待确认队列。
3. **别名限定**：明确同义的名称才写入别名表。同属后端的 Java 和 Go 岗位可以共享父类别，但不意味着它们是同一实体，不能绕过现有互斥规则强行合并。
4. **可信度限定**：依据标注集决定接受、审核、拒绝的边界；不把 LLM 自报信心或余弦分数直接当作校准概率。
5. **展示限定**：常用大类优先，详细岗位和标签二级筛选；保留搜索、展开、待确认数量提示。频次只用于排序，不作为真假判定。

一篇帖子提及多个公司和岗位时，进一步保存逐条公司—岗位证据关联。当前先分别提取列表再组合，可能产生原文没有表达的组合；不能仅通过字符串归一修正这个关系问题。

## 6. 如何落地和验收

1. 全量审核现有 234 个条目并回看原文，形成初版类别、别名和排除样本；覆盖高频词及有效小众岗位。构建独立的帖子级抽取验证集，避免只评名称而忽略上下文。
2. 增量增加岗位提及记录、类别映射和审核状态，保留旧 ID、名称与关联。对历史数据先生成迁移预览，区分确定映射、待确认、非岗位和范围外岗位，不直接删除或把所有未知名称塞入“其他”。
3. 为新抽取增加证据和合法类别校验，升级提取缓存版本。将待确认结果隔离于正式类别统计，提供回看原文的审核路径。
4. 在映射审核后切换筛选接口及聚合查询。分类层变化会影响分组、计数、摘要与缓存，需要版本化缓存并对受影响摘要进行预算受控的重建；不应为了标签变化重建全部问题向量。
5. 保留旧读路径和分类版本，能够撤销映射或切回旧版。正式迁移和历史重新抽取需单独审查。

评测应包含岗位证据抽取精确率/召回率、分类 macro-F1 和按篇次加权结果、部门/产品泄漏率、待确认覆盖率、有效小众岗位保留率，以及公司—岗位关联准确率。不要仅报告总体准确率：高频类别可能掩盖长尾误判。

本次验证：日期缓存与相关目录缓存回归测试 10 项通过；前端 TypeScript 检查通过；浏览器验证公司切换、公司内岗位搜索、摘要展示、全局折叠/展开和低频岗位搜索。Ruff 对目录路由仍报告原有 3 处 FastAPI `Depends` 参数默认值 B008，未改动这些接口签名。

本次没有修改认证、数据库结构、岗位提取提示词或历史岗位数据。后续关键工作是分类体系和历史映射治理，单纯收起列表只是改善交互。
